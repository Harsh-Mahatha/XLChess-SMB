## From the Development Guide

### Testing, Operations & Delivery

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

Deliver a fully working, maintainable SMB, not a caption-generation demonstration. Test each stage independently and end-to-end, including research, fact verification, image integrity, approval, scheduling, publication, retries, auditability and correction feedback. Evaluate both the cost of generation and the amount of human editing still required.

### Testing requirements

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

The developer must provide automated tests covering the critical parts of the system.

### Unit tests

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

Test configuration validation, scheduling, timezone handling, rating calculations, phase detection, content schema validation and deduplication.

### Integration tests

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

Test source adapters with recorded fixtures, research package creation, database persistence, image rendering and publishing adapters with mocked provider responses.

### End-to-end tests

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

Test the complete lifecycle:

```text
Trigger → Research → Verify → Generate → Render → Review → Approve → Publish
```

Also test rejection, regeneration, source outages, licence failures, invalid data, partial publication failures and recovery after downtime.

### Image integrity tests

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

For the World Championship reference, confirm that the original photographs are used directly.

The renderer must not replace them with AI-generated approximations.

Store the source file hash and test that any changes to the rendered photograph region are limited to the documented crop, scaling, rotation and encoding operations.

### Reliability, security and acceptance

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

Use durable queue state, job leases, heartbeats, bounded retries, idempotent completion, checkpointing where practical and recovery after crashes, disconnections or reboots. A lost worker must not lose the job permanently or cause duplicate posts. Protect device credentials, use HTTPS and least-privilege permissions, keep the model server local-only, and **do not put social-media publishing credentials on the PC**.

The developer must demonstrate: **run one installer → pair the PC → receive a queued XLChess job → generate using the RTX 4070 → return a complete result → review it in XLChess → recover after an interrupted job and a PC restart**. The owner should not need further PC-side configuration. Because Windows 10 is past normal support, the developer must assess the security implications and document a supported-OS migration path without making manual OS work part of ordinary SMB administration.

Build one reusable, configuration-driven pipeline for all post types and channels. Develop it incrementally, but deliver all six components, all 18 post-type categories and all listed channel integrations as part of the completed SMB.
