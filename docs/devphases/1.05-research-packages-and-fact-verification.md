## Scope

Normalise events, players, games and news; resolve duplicates, verify ratings/results/dates against authoritative sources and produce cited research packages with confidence and retrieval times.

## Done when

Every publishable claim is backed by retrievable source evidence; conflicts and outages block or flag unverified claims.

## From the Development Guide

### Research workflow

*Source: DEVELOPMENT_GUIDE.md 2.3 Data Sources & Content Generation*

When a post becomes due:

1. Load the post configuration.
2. Determine which information is required.
3. Select the appropriate approved sources.
4. Retrieve current information.
5. Normalise the retrieved records.
6. Resolve duplicate records and player/event identities.
7. Cross-check important claims.
8. Produce a structured research package.
9. Pass the research package to the content generator.

The research package should include factual claims, their source URLs, retrieval times, event times and confidence/verification status.

For example, a post about a player's rating decline requires the rating at the starting date and the current published rating, both for the same rating category.

The difference should be calculated programmatically:

```text
Rating change = Current rating − Starting rating
```

The language model must not be responsible for inventing or independently calculating authoritative statistics when deterministic code can do the calculation.

### Source reliability

*Source: DEVELOPMENT_GUIDE.md 2.3 Data Sources & Content Generation*

Use the following hierarchy:

- **Official source:** Preferred for results, rankings, ratings, qualification and regulations.
- **Structured tournament feed:** Preferred for game data where authorised and reliable.
- **Established chess publication:** Used for context, analysis and news.
- **Unverified external material:** Not automatically publishable.

Conflicting information must be recorded and either resolved against an authoritative source or sent for human review.

Source failures must not silently turn into fabricated content.

### AI safeguards

*Source: DEVELOPMENT_GUIDE.md 2.3 Data Sources & Content Generation*

Treat retrieved webpages and other external text as untrusted data.

The model must not follow instructions embedded in articles, source documents or image metadata.

Generated content must be checked against the research package. Claims without adequate evidence must be removed or flagged.

The system should also validate that the AI has not invented player ratings, tournament dates, match results, quotations or official announcements.

## From the Feature Definition

### Data Collection & Research

*Source: FEATURES.md 1.2.2 Data Collection & Research*

Collects reliable chess information from approved sources and prepares evidence that the rest of SMB can use. Every claim must be traceable to its source; conflicting or unavailable information must not be invented.

### Data sources and research

*Source: FEATURES.md 1.2.2 Data Collection & Research*

SMB must use a defined registry of approved chess information sources. The developer must not build a system that performs unrestricted internet searches and automatically treats the results as factual.

Every source should have a known purpose, reliability level, access method and usage policy.

### Core principles

*Source: FEATURES.md 1.1 Overview*

The following principles must guide the development.

1. **Automation first.** The system should not depend on humans supplying topics or researching information.
2. **Configuration-driven.** Posting rules, sources, frequencies and channels must be defined through configuration rather than hardcoded for each post.
3. **Evidence-based content.** Claims about players, tournaments, rankings and results must be supported by reliable data.
4. **Human approval.** SMB must never publish unapproved content.
5. **Image integrity.** Original photographs must not be altered by AI. Cropping, resizing, rotating and positioning are permitted.
6. **Legal image use.** Every external image must have its licence verified individually.
7. **Reusable architecture.** Adding a new post type should primarily involve adding configuration, not creating an entirely new implementation.
8. **Continuous improvement.** Human corrections should be recorded and used to improve future generations.
9. **Reliability.** Scheduling, duplicate prevention, retries, publishing and failure recovery must be handled systematically.
10. **Traceability.** We must be able to identify which sources, data, images, prompts and approvals produced every published post.
