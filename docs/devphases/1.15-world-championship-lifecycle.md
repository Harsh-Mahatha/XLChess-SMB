### Three-phase lifecycle

*Source: DEVELOPMENT_GUIDE.md 2.2 Post Types, Configurations & Triggers*

**Phase 1 — Pre-Tournament**
Every Friday at 09:00 UTC, research and publish information about the upcoming championship: participants, qualification, dates, venue, format, player developments and other relevant news.

**Phase 2 — During Tournament**
Suspend the weekly schedule. After each completed game, generate a post covering the result, updated match score, important moments, championship situation and next game.

**Phase 3 — Post-Tournament / Next Cycle**
Resume Friday posting. Initially cover the championship outcome, then progressively transition to the next qualification cycle, Candidates Tournament and next championship.

Repeat automatically for the next championship.

### Automatic phase detection

*Source: DEVELOPMENT_GUIDE.md 2.2 Post Types, Configurations & Triggers*

The developer must not rely solely on calendar dates.

The system should maintain a structured championship record containing:

- Tournament identity and cycle
- Official scheduled start and end dates
- Confirmed actual start
- Current game number and status
- Match score
- Official completion status
- Next-cycle information

Phase detection rules:

- `PRE_TOURNAMENT`: The championship has not started, based on verified event status.
- `DURING_TOURNAMENT`: The championship has officially started and has not concluded.
- `POST_TOURNAMENT`: The championship has officially concluded and the next cycle is being tracked.

Use official FIDE information as the authority for tournament identity and lifecycle. Other sources can provide supporting data.

If authoritative sources disagree or the current state is uncertain, flag the record for review rather than guessing.

### Game-completion triggers

*Source: DEVELOPMENT_GUIDE.md 2.2 Post Types, Configurations & Triggers*

A game-completion event must contain:

- Championship and game identifiers
- Both players
- Official result
- Updated match score
- Completion timestamp
- Source reference
- Verification status

A game is considered complete only when a reliable source confirms its final result. A clock stopping, broadcast interruption or temporary feed status must not independently trigger publication.

The system must distinguish individual games from rounds, and avoid generating multiple posts for the same completed game.

Use an idempotency key such as `world-championship-2026:game-1:result` to prevent duplicates.

If a result is later corrected, update the existing content record and flag any published post for review.

### Avoiding repetitive content

*Source: DEVELOPMENT_GUIDE.md 2.2 Post Types, Configurations & Triggers*

Weekly posts should not repeat the same information without a meaningful new development.

For example, the first post might introduce the players; subsequent posts might cover rating movements, qualification stories, preparation, the match format or significant news.

Maintain a history of published topics and compare new candidates against it.

If there is insufficient fresh information, the system may select a genuinely different evergreen angle or flag that no worthwhile post is available. It should not invent developments merely to satisfy a schedule.

## From the Feature Definition

### Story selection

*Source: FEATURES.md 1.2.3 Story Selection & Fact Verification*

For a World Championship post, potential angles might include:

- The champion's rating movement since winning the title.
- The challenger's recent performance.
- A major qualification milestone.
- A significant difference between the players.
- An interesting historical comparison.
- A newly announced match detail.

SMB should rank these angles and choose the strongest one supported by the available evidence.

Store the reason for selecting each angle so reviewers can understand the decision.
