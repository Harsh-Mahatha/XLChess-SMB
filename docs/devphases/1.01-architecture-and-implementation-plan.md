## From the Development Guide

### Mandatory architecture — XLChess job queue and 24/7 local AI worker

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

**This is a required part of SMB, which is part of XLChess, not XLChessOps.** I have a PC at home that is already running 24/7 and connected to the internet. **We will use my home PC to run the AI models for SMB.** XLChess will queue the jobs, set their priorities and manage the results. My home PC will take jobs from the queue, process them using locally installed open-weight AI models and send the output back to XLChess. XLChess will handle reviewing and publishing the completed posts. I only want to run a one-time setup script on my PC; after that, the developer should be able to manage the worker, models and configuration through XLChess. If necessary, I can arrange a remote-control session so the developer can access my PC for setup or troubleshooting.

### Available worker hardware

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

This home PC is a Windows 10 Home 64-bit machine with an Intel Core i7-8700K (6 cores / 12 threads), NVIDIA RTX 4070 (12 GB VRAM), 64 GB RAM, a 500 GB SSD and additional storage. Design for this machine, benchmark actual GPU memory and processing time, and make it possible to add or replace workers later. A quantised Qwen3 8B model through Ollama (or a comparably suitable local model runner) is a starting candidate, **not a mandatory model choice**. Prefer an open-weight model that can run without a paid per-request API; document model licence and hardware costs.

### Job flow and capacity

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

1. XLChess queues post-production and supporting AI jobs with an ID, input data, priority, configuration version and expected output format.
2. The PC worker **polls the XLChess API over outbound HTTPS**, securely claims the next available job, and runs the necessary local model and processing steps. No public inbound port, exposed model API or permanent remote desktop connection is needed.
3. The worker sends heartbeats and progress while processing, then returns the generated content, supporting artifacts, status, errors and timing to XLChess.
4. XLChess stores the results and makes completed posts available for human approval. Publishing is performed separately by XLChess **only after approval**.

**Do not impose a fixed daily post-production limit or a guaranteed five-post minimum.** Keep the worker busy whenever eligible jobs are queued, subject to safe concurrency and resource limits. If a post takes ten hours, the PC may produce only about two per day; if it can produce more, it should. Begin with one GPU-intensive job at a time and benchmark before increasing concurrency. Prioritise time-sensitive tournament stories and expire or reconsider stale work.

### One-time, script-driven installation on the PC

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

The developer **must provide one primary PowerShell installer**, for example `setup-xlchess-worker.ps1`, so the PC owner performs only a short, one-time setup. The script must:

- Check OS, GPU and driver compatibility, available RAM, disk space and internet access; install prerequisites where practical and give clear, actionable errors otherwise.
- Install and configure the local AI runner, download the selected model, install the XLChess worker and create its working folders and logs.
- Register the machine with XLChess using a short-lived pairing code or similarly simple secure process, without manually editing credentials, environment files or application configuration.
- Configure unattended background operation and automatic startup after reboot, with restart on failure. Check that Windows sleep or hibernation will not unexpectedly stop the 24/7 worker, and offer to configure appropriate plugged-in power settings with the owner's consent. If a reboot is required during setup, support a clear resume path.
- Run an end-to-end test job, verify actual GPU acceleration, upload its output to XLChess and display a concise success or diagnostic report.
- Supply scripted worker update, repair, diagnostics and uninstall procedures.

**Docker is optional, not a requirement for the owner.** Use native Windows installation if simpler. If containers are chosen, the same installer must handle all Docker/container setup automatically. The owner must not have to manually configure Docker, Python packages, model files, ports or services. A developer-assisted remote-control session is an acceptable fallback for unusual installation problems, not the normal operating model.

### Management through XLChess

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

After initial pairing, routine administration must be available through the XLChess web application: worker online/offline state, current job, queue and priorities, completed and failed jobs, processing time, health and GPU usage, logs, pause/resume, retries, concurrency and resource limits, model selection/downloads, prompts, configuration versions and controlled worker updates. Configuration changes must reach the PC without requiring the owner to log in and edit files.

### Reliability, security and acceptance

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

Use durable queue state, job leases, heartbeats, bounded retries, idempotent completion, checkpointing where practical and recovery after crashes, disconnections or reboots. A lost worker must not lose the job permanently or cause duplicate posts. Protect device credentials, use HTTPS and least-privilege permissions, keep the model server local-only, and **do not put social-media publishing credentials on the PC**.

The developer must demonstrate: **run one installer → pair the PC → receive a queued XLChess job → generate using the RTX 4070 → return a complete result → review it in XLChess → recover after an interrupted job and a PC restart**. The owner should not need further PC-side configuration. Because Windows 10 is past normal support, the developer must assess the security implications and document a supported-OS migration path without making manual OS work part of ordinary SMB administration.

Build one reusable, configuration-driven pipeline for all post types and channels. Develop it incrementally, but deliver all six components, all 18 post-type categories and all listed channel integrations as part of the completed SMB.

### Recommended technical architecture

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

The developer should build SMB as a modular system with a shared processing pipeline.

Given XLChess's early-stage requirements, I recommend TypeScript, Node.js, PostgreSQL and a queue-based worker architecture.

This is a recommended implementation, not a requirement to introduce unnecessary infrastructure.

### Technology stack

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

| Component | Recommended technology | Purpose |
|---|---|---|
| Language | TypeScript | Shared types and reliable interfaces |
| Backend | Node.js | Core SMB services |
| Database | PostgreSQL | Configurations, posts, approvals and history |
| Frontend | React / Next.js | Admin and review interface |
| AI generation | OpenAI API or configurable model provider | Research interpretation, story selection and writing |
| Image processing | Sharp | Preserve and composite original photographs |
| Graphic rendering | SVG / HTML / CSS / Playwright | Produce final graphics |
| Scheduling | Cron-based scheduler | Fixed recurring jobs |
| Background processing | Database-backed jobs initially | Asynchronous execution and retries |
| Object storage | S3-compatible storage or Supabase Storage | Original images and generated assets |
| Validation | Zod or JSON Schema | Configuration and AI output validation |
| Monitoring | Structured logs and error alerts | Operational visibility |

Use existing XLChess infrastructure where practical. For example, if PostgreSQL and Supabase are already in use, SMB can reuse those services rather than introducing a second database platform.

Avoid adding Redis, a dedicated message broker or multiple microservices until the workload justifies them.

### Logical architecture

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

- SMB Admin & Review Interface
- SMB Backend / Orchestrator — controls the post lifecycle and state transitions
- Configuration Manager
- Scheduler & Event Monitor
- Source Adapters
- Research & Verification
- AI Content Generator
- Image & Template Engine
- Approval Manager
- Publishing Adapters
- PostgreSQL + Asset Storage + Job Queue

The orchestrator manages state and invokes the appropriate services. It should not contain source-specific scraping logic, image rendering code or platform-specific publishing implementations.

### Development plan

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

The system should be built incrementally, with a working end-to-end pipeline established before expanding to every post type.

**Phase 1 — Understand and design**
Study the SMB overview, 18-category hierarchy, World Championship configuration and previous trial post. Define the database, schemas, interfaces, workflow states and technical architecture.
*Deliverable:* approved technical design and implementation plan.

**Phase 2 — Data collection**
Build the source registry and initial adapters. Start with one source and one post type. Retrieve real data, normalise it and create verified research packages.
*Deliverable:* working research pipeline with tests.

**Phase 3 — Content generation**
Implement story selection, three candidate versions, structured output validation and source-linked claims.
*Deliverable:* three factually grounded candidates generated from real research.

**Phase 4 — Image pipeline**
Implement licensed image discovery, licence records, asset storage and deterministic template rendering. Recreate the Gukesh–Sindarov trial using the original photographs without generative alterations.
*Deliverable:* publication-ready graphic with verifiable source and licence records.

**Phase 5 — Review interface**
Build the candidate comparison, editing, regeneration, rejection and approval workflow.
*Deliverable:* a reviewer can take a generated post through to an approved version.

**Phase 6 — X publishing**
Integrate X publishing with secure authentication, media uploads, duplicate prevention, scheduling and publication tracking.
*Deliverable:* first approved post published successfully to X.

**Phase 7 — Full automation**
Add recurring scheduling, event detection, recovery, phase transitions and historical content tracking.
*Deliverable:* posts are generated automatically without manual topic selection.

**Phase 8 — Complete and improve**
Add more post types, Facebook, Instagram and Discord. Improve templates and prompts using recorded feedback.
*Deliverable:* SMB continuously processing eligible queued jobs up to safe worker capacity and producing review-ready posts, with progress toward the unedited-approval target.

### Final direction

*Source: DEVELOPMENT_GUIDE.md 2.6 Testing, Operations & Delivery*

SMB is an automated content-production system, not merely a scheduler. A reviewer should receive as many finished, verified posts as the available worker can safely produce and concentrate on approval and creative improvement rather than gathering information or making graphics from scratch.

## From the Feature Definition

### Purpose

*Source: FEATURES.md 1.1 Overview*

The Social Media Bot (SMB) is an automated system designed to manage the research, creation, scheduling and publication of XLChess social media content.

The objective is to automate the work of a social media content team, not simply automate the act of posting.

SMB must independently determine what content is relevant, research the necessary information, identify suitable images, generate finished social media posts and submit them for human approval.

A human should not need to research chess news, decide what to post, find photographs, write captions or manually schedule routine content.

The human's primary responsibility should be to review the generated output, make creative improvements where necessary and approve publication.

### Why we are building SMB

*Source: FEATURES.md 1.1 Overview*

XLChess is an early-stage chess platform. Building an audience before launch and continuing to grow that audience after launch are important parts of our customer acquisition strategy.

Maintaining an active social media presence normally requires several roles: researchers, content writers, graphic designers, editors and social media managers.

SMB is intended to automate most of this work.

The operating model is for one person to review the completed posts produced by the available worker capacity, rather than manually research, write and design them.

Over time, we want one person supported by SMB to perform work that would otherwise require a larger content team.

### Core principles

*Source: FEATURES.md 1.1 Overview*

The following principles must guide the development.

1. **Automation first.** The system should not depend on humans supplying topics or researching information.
2. **Configuration-driven.** Posting rules, sources, frequencies and channels must be defined through configuration rather than hardcoded for each post.
3. **Evidence-based content.** Claims about players, tournaments, rankings and results must be supported by reliable data.
4. **Human approval.** SMB must never publish unapproved content.
5. **Image integrity.** Original photographs must not be altered by AI. Cropping, resizing, rotating and positioning are permitted.
6. **Legal image use.** Every external image must have its licence verified individually.
7. **Reusable architecture.** Adding a new post type should primarily involve adding configuration, not creating an entirely new implementation.
8. **Continuous improvement.** Human corrections should be recorded and used to improve future generations.
9. **Reliability.** Scheduling, duplicate prevention, retries, publishing and failure recovery must be handled systematically.
10. **Traceability.** We must be able to identify which sources, data, images, prompts and approvals produced every published post.

### What SMB must automate

*Source: FEATURES.md 1.1 Overview*

| Stage | What it does |
|---|---|
| Post Type Configuration & Scheduling | Determines which post is due and why |
| Data Collection & Research | Retrieves current chess information from approved sources |
| Story Selection & Fact Verification | Identifies the strongest angle and validates factual claims |
| Content & Image Production | Creates three candidate captions and finished graphics |
| Human Review & Approval | Approve, edit, reject or regenerate |
| Publishing, Monitoring & Feedback | Publishes to configured channels and records results |

Each stage must have clearly defined inputs, outputs, failure handling and status tracking. This allows the stages to be tested independently.

### Quality objective

*Source: FEATURES.md 1.1 Overview*

The system should improve until every original SMB-generated post can be approved without modification for ten consecutive days at the required posting volume. Human approval remains mandatory; the quality target does not authorise automatic publishing.
