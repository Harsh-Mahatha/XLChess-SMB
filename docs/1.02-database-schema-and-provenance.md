## From the Development Guide

### Database design

*Source: DEVELOPMENT_GUIDE.md 2.1 Development Approach & Architecture*

The database must support the complete lifecycle, not just store published captions.

Recommended core tables:

| Table | Purpose |
|---|---|
| `post_types` | Post-type identifiers and metadata |
| `post_configs` | Versioned configurations and scheduling rules |
| `data_sources` | Approved source registry |
| `source_records` | Retrieved information and provenance |
| `research_packages` | Verified research for each posting opportunity |
| `post_opportunities` | Scheduled or triggered work |
| `post_candidates` | Three generated versions |
| `media_assets` | Original and generated images |
| `media_licenses` | Licence evidence and restrictions |
| `review_actions` | Approvals, edits, rejections and feedback |
| `publications` | Channel-specific publishing attempts and results |
| `jobs` | Background tasks, retries and failures |
| `post_metrics` | Quality and performance measurements |

Use immutable identifiers, timestamps and version numbers where appropriate.

Important relationships include:

- One posting opportunity has one or more research packages.
- One posting opportunity normally produces three candidates per generation cycle.
- One candidate can have multiple revisions.
- One approved revision can be published to multiple channels.
- Each channel publication has its own status.
- Every generated asset links back to its original source and licence record.

The developer should also implement retention and deletion policies for downloaded images, external source data and generated media.

### Configuration requirements

*Source: DEVELOPMENT_GUIDE.md 2.2 Post Types, Configurations & Triggers*

Each subtype requires a configuration containing:

| Field | Description |
|---|---|
| `id` | Stable identifier, e.g. `1.1` |
| `name` | Human-readable name |
| `enabled` | Whether the subtype is active |
| `sources` | Approved data source identifiers |
| `imageSources` | Approved image source identifiers |
| `channels` | X, Facebook, Instagram, Discord |
| `schedule` | Fixed time, frequency or event trigger |
| `timezone` | Timezone for scheduled execution |
| `phases` | Optional lifecycle-specific behaviour |
| `contentRules` | Required facts, tone, structure and restrictions |
| `imageRules` | Image selection and composition requirements |
| `approvalRequired` | Whether human approval is mandatory |
| `priority` | Importance relative to other posts |
| `deduplication` | Rules preventing repeated content |
| `retryPolicy` | Failure and retry behaviour |

Configurations should be stored as version-controlled JSON or equivalent typed configuration, with schema validation.

A database may maintain runtime overrides, but the underlying configuration must remain understandable, testable and auditable.

### Research workflow

*Source: DEVELOPMENT_GUIDE.md 2.3 Data Sources & Content Generation*

When a post becomes due:

1. Load the post configuration.
2. Determine which information is required.
3. Select the appropriate approved sources.
4. Retrieve current information.
5. Normalise the retrieved records.
6. Resolve duplicate records and player/event identities.
7. Cross-check important claims.
8. Produce a structured research package.
9. Pass the research package to the content generator.

The research package should include factual claims, their source URLs, retrieval times, event times and confidence/verification status.

For example, a post about a player's rating decline requires the rating at the starting date and the current published rating, both for the same rating category.

The difference should be calculated programmatically:

```text
Rating change = Current rating − Starting rating
```

The language model must not be responsible for inventing or independently calculating authoritative statistics when deterministic code can do the calculation.

### Image licence verification

*Source: DEVELOPMENT_GUIDE.md 2.4 Image Sourcing & Graphics*

Every photograph must be verified individually.

Store:

- Original image URL and source page.
- Photographer and copyright holder, where identified.
- Licence type and version.
- Whether commercial use is permitted.
- Whether modifications are permitted.
- Attribution requirements.
- Licence URL and verification date.
- Any share-alike or other obligations.
- A copy or record of the licence evidence.

A photograph being visible on a free website does not automatically mean XLChess can use it.

Do not use images with non-commercial restrictions for XLChess promotional content without separate permission. Other restrictions, including no-derivatives requirements, must be assessed against the intended use.

If suitable licensing cannot be established, reject the photograph.

### Job states

*Source: DEVELOPMENT_GUIDE.md 2.2 Post Types, Configurations & Triggers*

Pending → Researching → Generating → Awaiting Review → Approved → Scheduled → Publishing → Published

Rejected, deferred and failed states branch from the relevant stages, with controlled recovery paths.

A failure in one stage must not require the entire workflow to restart unnecessarily.

For example, a failed Instagram publication should not regenerate the approved image or republish the post to X.

## From the Feature Definition

### Core principles

*Source: FEATURES.md 1.1 Overview*

The following principles must guide the development.

1. **Automation first.** The system should not depend on humans supplying topics or researching information.
2. **Configuration-driven.** Posting rules, sources, frequencies and channels must be defined through configuration rather than hardcoded for each post.
3. **Evidence-based content.** Claims about players, tournaments, rankings and results must be supported by reliable data.
4. **Human approval.** SMB must never publish unapproved content.
5. **Image integrity.** Original photographs must not be altered by AI. Cropping, resizing, rotating and positioning are permitted.
6. **Legal image use.** Every external image must have its licence verified individually.
7. **Reusable architecture.** Adding a new post type should primarily involve adding configuration, not creating an entirely new implementation.
8. **Continuous improvement.** Human corrections should be recorded and used to improve future generations.
9. **Reliability.** Scheduling, duplicate prevention, retries, publishing and failure recovery must be handled systematically.
10. **Traceability.** We must be able to identify which sources, data, images, prompts and approvals produced every published post.
